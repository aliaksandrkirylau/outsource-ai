# 03 — Команда агентов

Принцип из ADAPT: **сильная модель думает и проверяет, быстрая делает по
хорошему брифу, самая лёгкая ищет.** Модель и уровень усилия задаются на роль,
а не на тикет; внутри роли усилие можно поднять для сложного тикета.

Модели названы по классу. Сейчас это Claude: **Opus** (сильная), **Sonnet**
(быстрая), **Haiku** (лёгкая). Конкретные версии берутся из актуальной линейки
на момент внедрения.

## Роли

| Роль | Этап | Модель | Усилие | Основание |
|---|---|---|---|---|
| Аналитик проекта | 0 — знакомство с проектом | Opus | высокое | ◇ новое |
| Диспетчер (оркестратор) | 1, 7 + передача между этапами | Opus / детерминированный скрипт | среднее | ✓ ADAPT — сессия-оркестратор |
| Исследователь | 2 — ресёрч и драфт спеки | Opus | высокое | ✓ ADAPT — `/draft-ticket` |
| Ревьюер спеки | 3 — ревью спеки | Opus | высокое | ✓ ADAPT — ревью драфта во второй сессии |
| Разработчик | 4 — реализация | Sonnet | среднее; высокое для сложных | ✓ ADAPT — `/work-ticket` |
| Тестировщик | 5 — тестирование | Sonnet | высокое | ◇ новое |
| Ревьюер кода / чистильщик | 6 — чистка и ревью | Opus | среднее | ◇ новое |
| Справочный | любой — быстрые поиски | Haiku | — | ✓ ADAPT — `haiku-lookup` |

## Карточки ролей

### Аналитик проекта
- **Вход:** репозитории, документация, PM/BA-материалы, ответы человека.
- **Выход:** `PROJECT-PROFILE.md`, `CLAUDE.md` проекта, пустые журналы.
- **Нельзя:** менять код; додумывать то, чего нет в источниках — вместо этого
  вопрос человеку.

### Диспетчер
- **Вход:** событие трекера, статусы, отчёты агентов.
- **Выход:** запуск следующего агента, статусы и комментарии в трекере, ветка
  и PR, обновлённый `HANDOFF.md` проекта.
- **Нельзя:** делать работу этапов самому (на ADAPT оркестратор, которому
  разрешали всё, сам бросался драфтить и реализовывать — `05-lessons-learned.md`
  урок 1); держать в своём контексте дампы файлов — их читают субагенты,
  диспетчер хранит выводы.
- **Открытый вопрос:** агент или детерминированный конвейер с агентами на
  решениях (`08-open-questions.md`).

### Исследователь
- **Вход:** тикет, эпик, соседние тикеты, журнал находок, профиль, код.
- **Выход:** `tickets/<KEY>.md` в статусе `DRAFT`.
- **Нельзя:** реализовывать; класть догадки в критерии приёмки.

### Ревьюер спеки
- **Вход:** драфт, код, профиль.
- **Выход:** вердикт (принято / доработать / нужен человек) с доказательствами
  (файл:строка, вывод команды); `CONFIRMED` в спеке.
- **Нельзя:** переписывать спеку за исследователя целиком; принимать
  утверждение без проверки.

### Разработчик
- **Вход:** спека в статусе `CONFIRMED`, профиль, скиллы проекта.
- **Выход:** изменения в ветке, записи в журналах, отчёт.
- **Нельзя:** выходить за скоуп; чинить чужое «заодно»; «исправлять» формулу
  клиента; объявлять «готово» без свежего вывода проверки; полировать после
  того, как проверки прошли (урок 5).

### Тестировщик
- **Вход:** спека, дифф, отчёт разработчика, профиль (матрица проверок,
  доступные среды, регрессионный набор).
- **Выход:** протокол проверки по каждому критерию; дефекты с
  воспроизведением; план ручной проверки для QA, если среда закрыта.
- **Нельзя:** править продуктовый код (только тесты); верить отчёту
  разработчика без перезапуска.

### Ревьюер кода / чистильщик
- **Вход:** дифф, спека, правила проекта.
- **Выход:** вычищенный дифф или возврат с замечаниями.
- **Нельзя:** рефакторить за пределами диффа; менять поведение.

### Справочный
- **Вход:** узкий вопрос «где X», «что написано в Y».
- **Выход:** короткий ответ со ссылками.

## Общие правила для всех агентов

Это обобщённый общий промпт агентов ADAPT (`framework/agents/`):

- прочитать `CLAUDE.md` проекта и следовать ему;
- делать ровно задачу из брифа;
- финальное сообщение — тому, кто запустил, а не человеку: что сделано, чем
  проверено (с выводом команды), что осталось открытым;
- длинные таблицы и логи — в файлы, в ответе — пути;
- без git-записи и записи в трекер, если это не роль диспетчера.

## Как писать бриф агенту (из практики ADAPT)

- Цель, а не пошаговый сценарий; что уже исключено; где лежат нужные файлы.
- Явный блок «экономная проверка» и ориентир по времени для разработчика.
- Проверяемые утверждения — с датой, файлом и строкой, чтобы принимающая
  сторона могла их перепроверить (урок 3).
- Явно сказать, какой агент, модель и усилие получил каждый запуск.
