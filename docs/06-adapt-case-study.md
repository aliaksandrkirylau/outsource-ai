## Проект

Аутсорс-проект: аналитический продукт для ритейла с чатом на естественном
языке. Четыре независимых репозитория (фронтенд, API-шлюз, аналитический
сервис, генератор тестовых данных), общая база. Работа шла по тикетам Jira.

**Фаза 1 сдана:** каталог из 37 бизнес-метрик заказчика работает
детерминированно; регрессионный набор — 148 эталонных вопросов (140/148
строго, 142/148 мягко); около 6,5 тыс. юнит-тестов. После сдачи — цикл
исправления багов заказчика по той же схеме.

## Цикл одного тикета на ADAPT

```
Владелец: «прочитай HANDOFF» → сессия-оркестратор резюмирует состояние и ждёт
Владелец, сессия 1: /draft-ticket KEY  → tickets/KEY.md (DRAFT)
Владелец, сессия 2: ревью драфта против кода → правки, открытые вопросы
Владелец: снимает вопросы, ставит CONFIRMED
Владелец, сессия 3: /work-ticket KEY   → код + журналы + отчёт
Оркестратор (по просьбе): проверка отчёта — пересчёт эталона, golden-реплей
Владелец: git (коммит, PR), статусы Jira, архив спеки
```

Для эпика целиком перед этим — `/verify-epic-plan`: план эпика, написанный
вне репозитория по документам, проверяется по коду, каждое утверждение —
гипотеза; результат — проверенный порядок тикетов и обновлённый реестр
расхождений со спекой.

## Что доказано

- **Разделение «драфт → ревью → реализация» работает**: ревью драфта ловило
  реальные ошибки до реализации.
- **Строгий скоуп + журнал находок** — десятки находок записаны с владельцем,
  ни одной поломки «заодно».
- **Дисциплина проверки** — правило «нет свежего вывода — нет "готово"»
  закрыло класс тихих ошибок.
- **Разные модели под разные роли** — Opus на ревью, Sonnet на реализации,
  Haiku на поисках.
- **Память проекта в файлах** — новая сессия входит в контекст по
  `HANDOFF.md` за минуты.

## Чего не хватало (= что добавляет целевая картина)

- Каждый переход между этапами — ручной запуск владельцем.
- Статусы Jira, ветки, коммиты, PR — вручную.
- Нет агента-тестировщика: исчерпывающе проверял живой QA, отчёт воркера
  перепроверял оркестратор по просьбе.
- Нет этапа чистки: стиль и лишние комментарии держались правилами в промпте,
  отдельной проверки не было.
- Специфика проекта не отделена от процесса: команды и скиллы ADAPT содержат
  имена коллекций, идентификаторы игрока, пути — их нельзя перенести на другой
  проект без переписывания. Поэтому во фреймворке появляется профиль проекта.
